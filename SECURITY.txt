LEAKCAM rev 1: security
=======================

What an attacker could get or do, what protects it today, and what is still open. Keep this file current when a
test, a design decision or a finding changes it (as SPEEDS.txt and ENERGY.txt). Findings name the test that found
them.


1. What is worth protecting
---------------------------

  - The Wi-Fi passphrase of the owner's network: stored on the BL616, sent once from the phone over BLE.
  - The pictures, clips and sound from inside the owner's home: sent to the server.
  - The device itself: firmware that could be replaced, a camera and microphone that could be turned on.
  - The server: a device that can post to it could flood it or fake leak reports.


2. BLE provisioning (Wi-Fi credentials only)
--------------------------------------------

  What it does (DESIGN.md 5.3): on USB power the BL616 advertises as its serial (the device ID), a phone pairs, writes the SSID and
  the passphrase, the BL616 checks them (join, DHCP, internet) and stores them. BLE does nothing else.

  Pairing PIN (user, 2026-11-01: only a phone with the app may pair and configure Wi-Fi; against device hijack):
  LE Secure Connections passkey entry with a 6-digit PIN per device.
    - Each board holds its own PIN, pre-stored when its firmware is flashed (easyflash "pair_pin"; make flash runs
      tools/power-bringup/provision_pin.py: the device ID from the USB serial number, the PIN derived on the flashing
      host, written through the console). No key or derivation is built into the firmware image: dumping one image
      tells nothing about another board's PIN. A board without a stored PIN does not advertise.
    - How a PIN is derived (HMAC-SHA256 of the device ID under a 256-bit key, first 4 bytes mod 10^6) is known only to
      the flashing host and the presence server (server/: LEAKCAM_PIN_KEY in its env file, mode 600; the key's master
      copy .secrets/pairing_secret, outside git). The app holds no secret: it asks the server for the board's PIN
      (GET /v1/devices/<id>/pin) right before it pairs and enters it itself.
    - The provisioning service's characteristics need an authenticated link (passkey), so Just Works is refused: a
      phone without the app has no PIN and cannot pair or write (tests/test040).
    - Passkey entry also protects the pairing against an active man-in-the-middle (unlike Just Works), as long as the
      PIN stays secret.
    Remaining gaps: the PIN endpoint is open on the LAN until the server authenticates the app (section 4, test109);
    anyone holding the server key or the flashing host derives every PIN; a 6-digit PIN only resists online guessing
    (the board allows one pairing attempt per connection; no lockout yet).
  The link: P-256 ECDH, AES-CCM. Protects against passive sniffing (the passphrase never seen). Legacy pairing is not
  acceptable (crackle); LE Secure Connections must stay on.

  No USB power gate since 2026-11-01 (user: the pre-stored PIN is enough to prove the phone). BLE runs from boot;
  the board advertises always on USB power, and on battery only while no network is stored or presence is lost (60 s every 5 minutes,
  provision.c), so a new board is found without a cable and a configured one on battery is silent.
    - Written into the stored credentials only after a passed check (commit 0x01) or on request (0x02); never on a
      failed check or a dropped link.

  Findings (tests/test040, 2026-10-28), all fixed:
    - LE Secure Connections did not work: the SDK's profile for the BLE controller library we use
      (ble1m0s1bredr0) compiled out the host's ECC handlers while still offering Secure Connections; Android's
      pairing failed ("Unhandled SMP code 0x0c"). Fixed in firmware/bl616_common/sdk_patch.py (CONFIG_DISABLE_BT_ECC n).
    - The USB power gate could be bypassed: the host skips the consent callback when pairing follows the board's
      own Security Request, so the board paired while on battery. Fixed: the gate is at connection time.
    - The SDK printed every link key (LTK) to the console ("BLE LTK: ..."): anyone with the console or a log could
      decrypt a recorded session. Removed in sdk_patch.py. Rule: never print keys, passphrases or tokens; the test
      tools print only lengths and CRCs (pt_ble creds).

  Before 2026-11-01 (Just Works): anyone in radio range of a device on USB power could pair and overwrite the stored
  credentials. Now this needs the device's PIN (above). Reading the stored passphrase is not possible (write-only
  characteristics). Options kept for later (section 6): a pairing window of a few minutes after plug-in; an owner
  lock (only the first phone may change the credentials, a new one after a factory reset on the device).

  Bonds: the board does NOT keep bond keys (CONFIG_BT_SETTINGS off): they live in RAM until its next reset. The phone
  keeps its half, so after a board reset the phone must forget the device before it pairs again (test040 checks
  this). Open: either keep bonds (CONFIG_BT_SETTINGS, in easyflash) or pair without bonding, so the phone keeps
  nothing either (section 6).


3. Stored secrets on the board
------------------------------

  - wifi_ssid / wifi_psk: in easyflash (littlefs on the BL616's SPI flash), NOT encrypted. (BLE bond keys are not
    stored, section 2.)
    Anyone with the board in hand can read them: through the BL616 console (PR1 pads, inside the enclosure) or by
    reading the flash (UART/USB ISP boot, or the chip off the board).
    Accepted for now: whoever has the device in hand had the physical access anyway. Open: BL616 flash encryption
    and locking the ISP/JTAG with eFuses for production (section 6).
  - The passphrase is never printed: wifi_set (debug builds only) prints the SSID and the passphrase length.
  - pair_pin (the BLE pairing PIN): in easyflash, not encrypted, never printed (`provision` says only "stored"/"none").
    Anyone with the board in hand reads it like the credentials; it opens pairing to that one board only.
  - The phone app stores no Wi-Fi credentials (only each LEAKCAM's ID and name); the SSID is shown from the server
    (each check-in reports it: not secret), the passphrase never.


4. Network and server
---------------------

  Today (mock server, attic/firmware/k230_capture/mock_server.py): plain HTTP and RTMP, no authentication.
    - Anyone on the path can read the pictures, clips and sound, and fake the server's answers (e.g. "no leak",
      a different change net via "nn", a long "video" request).
    - Anyone can post fake reports as a device.
  Needed before real use (DESIGN.md 7 "The real server"):
    - TLS for /v1/check, /v1/nn, /v1/poll and the clips (RTMPS, or the server pulls over TLS).
    - A per-device identity (a key or certificate made at the factory or at first setup), so the server knows which
      device posts, and the device knows it talks to the real server (pinned server certificate).
    - Decided 2026-11-10 (user; DESIGN.md 5.3.12 "Design decision"): the check-in over mTLS; the server's key pinned
      (current + next); the device certificate long-lived (the server checks its dates); the board ignores the
      certificate dates ONLY on the first check while it has no clock (after a battery loss), takes the time from
      that verified answer's X-Time, and checks dates from then on. No plain fallback, time never from an
      unverified exchange.
    - Built 2026-11-10 for the BL616's requests (DESIGN.md 5.3.12 "Built"): one CA (tools/pki/leakcam_pki.py, P-256,
      20 years) for the server and every device; the CA certificate, the device certificate and its key in the
      board's flash (provision_tls.py at make flash); server :8443 mTLS only, CN = the device ID. Still plain: the
      app and the K230 on :8090 (the phone's TLS to the same CA and the K230's are next).
    - The change net ("nn") and thresholds from the server: check the CRC against a signed value, not only the
      transport.
  The presence server (server/, the Pi, plain HTTP on the LAN, use case 2): check-ins carry the device ID and the
  SSID (not secret); /v1/devices/<id> answers presence and SSID to anyone on the LAN; /v1/devices/<id>/pin gives
  the pairing PIN to anyone on the LAN (section 2). Both need app authentication before the server leaves the LAN.
  The Wi-Fi check at provisioning (wifi_check.c) fetches http://connectivitycheck.gstatic.com/generate_204 over plain
  HTTP and sends nothing of the owner's.


5. Firmware, debug and update
-----------------------------

  - Debug consoles: the BL616 shell (USB CDC on PR1) and the K230 console over the link; both inside the enclosure.
    LEAKCAM_RELEASE builds drop the debug-session wait and wifi_set (firmware/DEBUG.txt). Open: the release build's
    shell commands (isp, reboot, pt_*) - which stay in the product.
  - BL616 ISP boot (UART/USB) and K230 USB boot: anyone with the board open can flash any firmware. Open: secure
    boot / signed images on both chips, ISP and JTAG locked by eFuse for production.
  - OTA (DESIGN.md 7, not written yet): images must be signed and checked before ota_meta switches slots;
    a CRC alone does not stop a forged image.


6. Open items (to decide)
-------------------------

  1. Server: TLS, per-device identity, pinned server certificate (section 4).
  2. Signed OTA images and signed change nets (sections 4, 5).
  3. BL616 flash encryption for the credentials; eFuse locks for ISP/JTAG on both chips.
  4. Which shell commands stay in LEAKCAM_RELEASE builds.
  5. BLE pairing: the PIN endpoint needs app authentication (test109); a pairing window after plug-in and an owner
     lock (with an on-device factory reset, e.g. 3 plug-ins in 10 s) still open; a lockout after failed pairings.
  6. BLE bonds: keep them on the board (CONFIG_BT_SETTINGS) or pair without bonding (section 2).
  7. Remote Wi-Fi change (DESIGN.md 5.3.2, test123): the new passphrase goes app -> server -> board's check-in, which is
     plain HTTP today: encrypt it with a per-device key derived like the pairing PIN, drop it at the server once
     delivered; the change request needs the app authorized for that device (the device ID alone must not be enough,
     or anyone knowing an ID could move a board onto their own network).
